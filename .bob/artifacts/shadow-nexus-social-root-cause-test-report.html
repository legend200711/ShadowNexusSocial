Test 2 — Cloudflare Isolation

CLOUDFLARE CLEARED  The Cloudflare Worker (yellow-term-11e6.nthntjrn.workers.dev) is a pure API/R2 worker. It has zero HTML page serving, zero redirect logic, zero caching of application state. All its fetch() calls go outbound to PayPal, LiveKit, and the Cloudflare Stream API — never back to itself or to shadownexussocial.online.

The main site (shadownexussocial.online) is served entirely by Firebase Hosting. Cloudflare is only in the DNS path; it is not a proxy for the main site pages. The only Cloudflare involvement in a page load is media retrieval from R2, which the service worker routes as network-only and cannot loop.

There is no Cloudflare Page Rule, Worker Route, or Cache Rule that touches the main site's navigation requests based on the codebase evidence.

Test 3 — First Failed / Repeating Request

First request at risk:

In index.html at line 12442, immediately after onAuthStateChanged is registered, this listener fires:

onSnapshot(doc(db, 'siteSettings', 'config'), (snap) => { ... })

This listener fires immediately on first connection — before onAuthStateChanged has resolved. The Firestore security rule for siteSettings/config is allow read: if true (public), so the read itself succeeds.

The first request that can cause a loop is the snapshot callback's action, not the read itself:

If the document contains maintenanceMode: true, the callback executes window.location.replace('maintenance.html'). maintenance.html in turn contains its own onSnapshot(doc(db, 'siteSettings', 'config'), ...) which, when maintenanceMode is false, executes window.location.replace('index.html'). This creates a cross-page redirect loop.

⚠ SPA Rewrite + Maintenance Page Conflict:
The firebase.json hosting config has a catch-all SPA rewrite: "source": "**", "destination": "/index.html". If a browser navigates to maintenance.html and Firebase Hosting rewrites it to index.html, index.html loads, checks maintenanceMode=true, and redirects back to maintenance.html — which rewrites to index.html again. This is a confirmed loop path.

However: maintenance.html is present as a physical file in the hosting root, so Firebase Hosting serves it directly without invoking the rewrite. The rewrite only applies to paths that do not match a real file. This path is likely safe unless the rewrite evaluation order changes or the file is missing from a specific deployment.

Test 7 — Firebase Check

Auth initialization

Auth initializes via initializeApp / getAuth in a single module script at the top of index.html. The Firebase SDK version is 10.8.0 loaded from gstatic.com CDN — network-only per the SW. No double-initialization risk; getApps().length guard is present in firebase-config.js.

Firestore siteSettings/config listener (critical path)

This is the highest-risk listener. It fires on every cold page load, before auth resolves, and its callback contains:

if (cfg.maintenanceMode === true && currentUser) { window.location.replace('maintenance.html') }

The currentUser guard means this only redirects once auth has resolved — so if maintenanceMode=true is set in production Firestore and the loading user is not the Founder, they are always redirected to maintenance.html immediately after login.

The same check exists in the onAuthStateChanged block (line 12354–12367). Two independent redirect paths for the same condition.

Firestore listener timing

Both siteSettings/config and siteSettings/pageVisibility onSnapshot listeners are registered at module load time — before onAuthStateChanged fires. The rules correctly allow public read for both. This is safe.

The onAuthStateChanged callback awaits multiple sequential Firestore reads (getDoc(users/{uid}), another getDoc(siteSettings/config)). If Firestore is slow or these reads fail/timeout, the auth gate spinner remains visible — causing the appearance of a loading loop.

ROOT CAUSE

Firebase is the primary suspect. Cloudflare is cleared.

The most likely root cause is maintenanceMode: true present in the production siteSettings/config Firestore document. When this is true:

  • Every non-Founder user landing on index.html is immediately redirected to maintenance.html (via the onAuthStateChanged callback at line 12363 and/or the siteSettings onSnapshot at line 12459)
  • maintenance.html monitors the same doc and redirects to index.html when maintenance is off — but if the value is intermittent (e.g. being toggled), users ping-pong between the two pages
  • Multiple computers experiencing the same loop is consistent with a shared Firestore state, not a local code or cache issue

The secondary cause is a stale service worker (pre-v32) that still has the controllerchange → reload listener. The version.json explicitly documents this was fixed on 2026-08-28. Any device that has not cleared its SW cache still has the old SW and will loop on every SW update.

Cloudflare is confirmed not involved: the Worker has no redirect logic, no HTML proxying, no caching of pages, and no self-referencing fetch calls.

SAFE FIX (identify only — do not deploy until root cause is confirmed by browser DevTools)

  1. Check maintenanceMode in Firestore Console (read-only): Open Firebase Console → Firestore → siteSettings/config → verify maintenanceMode value. If it is true, that is the loop source.
  2. Browser DevTools — Network tab: Open DevTools, reload the looping page. Look for any request to maintenance.html. If it appears immediately after login, confirm maintenanceMode finding. If it never appears, move to the Auth timing investigation.
  3. Clear stale SW on affected machines: In Chrome: DevTools → Application → Service Workers → Unregister. Then hard-reload. If the loop stops on that machine, the stale SW (pre-v32) was the cause.
  4. Run the Firebase Emulator test: cd snx-emulator-test && npm run run-all. If all 11 tests pass, the production Firebase config (maintenanceMode, rules, or missing doc) is the cause — not the application code itself.
  5. If maintenanceMode is the confirmed cause: Set it to false in the Firestore Console (no code change, no deployment needed). This is a data fix, not a code change.
